# Session 2026-09-09 — the 80 minutes were not Opus, and correct shot detection broke the thing downstream of it

Picked up mid-flight from the 8 September session. Analysis had been left
running detached and had finished overnight: **10 shots, 36 errors,
`awaiting_confirmation`** on the test job `odnit6zfn623ay6y8j1ted2i` (23-second
vampire/bat animation). That confirmed the previous session's last fix — running
analysis as a detached worker — actually works.

Then two problems fell out of looking at the result, and a third fell out of
checking whether the product is safe to hand to users.

---

## 1. The latency was Grounding DINO, not Opus

Last session I said the remaining ~15 minutes of analysis was Opus and that
fewer frames per comparison was the way to attack it. **That was wrong.** The
run took **80.2 minutes**, and detection was not the cost — the pair
comparisons were cached and finished in seconds.

The time was in `write_errors`. Localizing one error runs Grounding DINO once
per keyframe — 5 keyframes per shot, up to ~60s each — and both loops were
sequential: one error at a time, one frame at a time.

**How the Firestore timestamps proved it.** Every error whose type is `lighting`
or `atmosphere` skips grounding entirely, and those were written in the *same
second* as each other. Every `prop`/`wardrobe`/`other` error landed almost
exactly **5 minutes** after the previous one:

```
10:35:53.804  atmosphere   ┐
10:35:54.096  lighting     │  7 errors, same second
10:35:54.190  atmosphere   │  (all skip grounding)
10:35:54.269  lighting     │
10:35:54.374  lighting     │
10:35:54.452  atmosphere   │
10:35:54.564  lighting     ┘
10:40:55.121  other        ← +5:00   one Grounding DINO pass
10:45:55.755  wardrobe     ← +5:00
10:50:56.478  other        ← +5:00
...
11:46:04.979  lighting     ← last, 80.2 min after the first
```

The gaps *are* the Grounding DINO calls. This is a reusable diagnostic: if
analysis is slow again, read `createdAt` on the errors before profiling
anything.

**Fix** (`41deb72`): both loops now run concurrently, with a semaphore in
`grounding.py` (`GROUNDING_CONCURRENCY = 12`) bounding total Replicate
predictions in flight so the two nested levels cannot cause 429s.

**Measured, not estimated** — same job, same cached comparisons, same 36 errors:

| | before | after |
|---|---|---|
| wall time | **80.2 min** | **8.9 min** |
| errors produced | 36 | 36 (identical) |

## 2. Correct shot detection turned every scene cut into a "continuity error"

Of the 36 errors, **28 were `lighting`/`atmosphere`/`other`** — and they were
not errors at all.

Once shot detection started finding all 10 cuts, comparing every pair meant
shot 1 was judged against shot 9. A deliberate cut from a stormy exterior to a
candlelit crypt came back as an *atmosphere error* instructing us to replace one
background with the other. Every shot was told to match a different reference
shot, and several instructions flatly contradicted each other:

| target | instruction |
|---|---|
| shot_0005 | "Regrade to introduce **warmer** amber tones" |
| shot_0009 | "Regrade to **reduce the warm** golden cast, match cooler tone" |
| shot_0007 | "Replace the crypt-and-coffin background with the dark warm-glow backdrop" |

If a user had confirmed those, the fix stage would have spent their credits
dismantling their film.

The detection prompt was actively causing this — it tells Opus *not* to return
`different_scene: true` for AI footage with dramatically different backgrounds.
That instruction was written when videos were mis-split into 2 shots, where it
was correct. Correct shot detection made it harmful.

**Fix** (`e36a518`): grade/style types (`lighting`, `atmosphere`, `other`) now
only compare between **adjacent** shots, where "these should match" is a safe
assumption. Object-level types are unchanged and still compare across every
pair — a temporal/causation error like bullet holes appearing before the
shooting is only visible between distant shots. Holistic detection is exempt by
design: judging one shot against the whole sequence is the sanctioned way to
catch a rogue clip.

Replayed against the 36 recorded errors (snapshotted first, at
`jobs/odnit6zfn623ay6y8j1ted2i/_snapshots/run-2026-09-09-80min`): **36 → 12**,
and what survives is the real set — sleep mask, fingernails, brooch, collar, bat
on chest, blue sparks.

Dedupe also stopped treating colour words as identity. "black painted
fingernails" and "fingernail color" were the same defect reported by two pairs
with zero word overlap; "black sleep mask" and "black fingernails" on the same
shot were different defects sharing only the colour. Colours are now stopwords,
plus trailing-s stemming: **12 → 11**.

**One genuine loss:** "the bat's eyes are open in shot 3, closed in shot 1"
(shots 1→3, type `other`) is discarded by the adjacency rule. Exempting `other`
would bring it back along with the visual-style noise.

## 3. The output was about to be judged by a standard the input was not

Found while checking whether the product is safe for users. `verify.py` computes
`scoreAfter` by re-running `detect_shots` and `compare_pair` over the
**finished** video — but the adjacency rule had only landed in detection.

A job whose fix worked perfectly would have come back labelled *"Aleph
introduced 25 new issues"* with a score of 0 — its own scene cuts counted as
damage the fix had done. The before/after number is the one thing the product
shows a user at the end.

**Fix** (`f3f68b0`): the rule is now one shared helper, `is_far_grade_error`,
used by both detection and verification.

## What the production data says about shipping this

The question was whether the next users will have a good time. The honest
answer is **no, not confirmable** — and the evidence is worth writing down.

**The fix stage — the part users pay for — has never been confirmed working in
the current architecture.**

| evidence | value |
|---|---|
| errors ever marked `verifiedResolved: true` | **1**, on 2026-06-03 |
| completed jobs with `verificationPassed` recorded | 3 — Aug 29, Aug 30, Sep 3 |
| of those, how many passed | **0** (all `fixesUnverified: 1`) |
| completed jobs warning "Aleph introduced N new issues" | ~25 of 62 |
| worst case | Aug 25: score **92 → 2**, marked `done` and delivered |

**And the numbers that looked good were an artifact.** The `87 → 100` and
`92 → 100` results that made the product look like it worked were produced by
the shot detection fixed on 8 September: verification found **one shot** in the
output and had nothing to compare it against, so it scored 100 by default.
Those numbers were never measuring repair.

**Two things that will hurt users regardless of fix quality:**

- **42% of uploads never start.** 25 of the last 60 jobs sit in `uploading` with
  0 shots. The upload instrumentation added on 8 September has never actually
  run, because there has been **no real traffic since 5 September**. The next
  user to upload is the experiment.
- **The score will read 0 for almost everyone.** `compute_continuity_score` is
  `100 - errors×8 - high×5`, which floors at zero past 12 errors. Correct shot
  detection finds more errors, so even a successful repair can show a 0. Not
  fixed.
