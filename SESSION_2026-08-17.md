# Session 2026-08-17 — "analysis stopped completing" incident

Diagnosis, six fixes, first deploy of either surface since June/July, and the
repository's first commit.

---

## The reported problem

PostHog showed the analysis step no longer completing for any user between
2026-08-12 06:31 and 2026-08-13 13:15. Ten job IDs, all with the same shape:
`job_created` and `job_analysis_started` fire, `video_uploaded` fires, the user
lands on `/job/<id>`, waits 40s–13min, goes back to `/` and re-uploads.

**The premise was wrong.** There was no regression on 12 August. The analysis
step never stopped completing.

---

## What was actually happening

`awaiting_confirmation` is the *successful* terminal state of the analysis
step. It has been the dominant status on every single day for 30 days,
including well before 12 August. `done` appeared exactly once in that window —
the "last job that completed end to end" was really the only user who ever
cleared the credit check and clicked Fix.

The ten "failures" were **three unrelated defects** that happen to produce the
same user experience — a page showing nothing:

| Bucket | Count | What actually happened |
|---|---|---|
| Analysis succeeded, found nothing | 5 of 10 | Shots + errors written; mostly 1-shot clips where detection is structurally near-blind |
| Plan rejection, silently relabelled | 3 of 10 | `status:"error"` overwritten back to `awaiting_confirmation` |
| Genuine crash | 2 of 10 | `[Errno 2]` on keyframe upload |

Everything outward was healthy. Verified with live calls, not inference:

- **Model API** — `claude-opus-4-8` resolves, HTTP 200, not deprecated or
  renamed. A vision call using a real production keyframe URL succeeded.
- **Storage** — public read, 200, valid JPEGs, nothing signed so nothing
  expires.
- **Timeouts** — 600s configured vs **3.41s** observed. 0.6% of budget.
- **Deploys** — frontend frozen since 3 Jun (that build was still serving
  scenefixer.com), Modal since 2 Jul, zero files touched 10–15 Aug.

### The worst part, found by actually loading the page

The progress rail ticked **"Splitting shots ✓"** and **"Scanning shots ✓"** on
a job rejected before transcoding ever ran, then said "0 errors found" and "No
inconsistencies detected yet."

It did not merely omit the reason — it affirmatively certified two phases that
never executed. That is very likely why nobody reported this as broken: they
were told it had succeeded.

## Fixes shipped

Seven commits. Baseline first, then one defect each.

```
40f8a41 fix: tick progress steps from evidence, not sequence position
6947e5d feat: emit server-side analysis outcome events to PostHog
8a7bd12 fix: give a finished analysis with no findings something to say
ed21956 fix: survive a keyframe that ffmpeg cannot extract
246c408 fix: render the video-length limit in whole seconds
b219373 fix: stop run_detect overwriting a terminal decompose error
7b72ded baseline: production state as deployed — frontend 3 Jun, Modal 2 Jul, pre-fix
```

### 1. Status overwrite (`modal_app/app.py`)

`run_decompose` signals a plan rejection by writing `status:"error"` + an
`errorMessage` and returning `0` **without raising**. `process_job` then called
`run_detect` unconditionally, which found zero shots and overwrote the status
with `awaiting_confirmation` — discarding the reason.

Now checks the return value and skips detect only when decompose left the job
in a terminal error state. Deliberately does **not** raise: raising would change
the failure semantics of every other decompose path.

### 2. Duration message (`modal_app/decompose.py`)

`0.5` min formatted with `{minutes:.1f}` produced *"supports up to 0.5 min, but
this video is 0.5 min"* for a 31s clip. Both sides now render in whole seconds,
with `ceil` on the measured duration so the two numbers can never print equal
(`round` would reproduce the same bug at 30.4s).

The `0.5` cap value itself is untouched — that is a pricing decision.

### 3. Keyframe crash (`modal_app/decompose.py`)

`ffmpeg -ss` past the last decodable frame of a shot writes no file and still
**exits 0**, so `check=True` was satisfied and `upload_keyframe` raised
`[Errno 2]`, killing the entire job. Both observed crashes were at `k=4` — the
0.90 offset, the only one that can overshoot a shot boundary.

`extract_keyframe` now verifies the file exists and is non-empty, returning
`None`; the loop logs the skipped shot/offset and continues.

### 4. Empty states (`components/JobStatus.tsx`)

`STATUS_BANNER` had no entry for `awaiting_confirmation`. Three outcomes, three
messages, deliberately not collapsed:

- **partial** — `shotsAnalyzed < shotCount`, "Analysed N of M shots"
- **single shot** — nothing to compare, ask for a clip with cuts
- **clean** — ≥2 shots, 0 errors, presented as a real result

`errorMessage` now renders whenever present, not only when `status === "error"`.

### 5. Instrumentation (`modal_app/analytics.py`, new)

Four server-side events, at the lines that decide an outcome:

| Event | Site |
|---|---|
| `job_analysis_completed` (`outcome:"analysed"`) | `detect.py` terminal update |
| `job_analysis_completed` (`outcome:"empty"`) | `detect.py` zero-shot return |
| `job_analysis_failed` | `app.py` `process_job` except |
| `job_analysis_rejected` | `decompose.py` plan-limit guard |

Timer starts once per `process_job`, so `duration_ms` spans decompose + detect.
`distinct_id` is `ownerUid` falling back to `beta_<token[:8]>`.

Every capture swallows its own exceptions and the client no-ops when the secret
is absent — verified with both env vars unset and the `posthog` package not
even installed. Telemetry cannot fail a job.

### 6. Honest progress rail (`components/JobStatus.tsx`)

Each tick now derives from evidence that the phase produced something:

| Step | Evidence |
|---|---|
| Uploading | `inputVideoUrl` |
| Splitting shots | `shotCount > 0` |
| Scanning shots | `scoreBefore` (written only on the path that analysed shots) |
| Review | `fixingStartedAt` |
| Fixing | `stitchVideoUrl` |
| Verifying | `outputVideoUrl` |
| Done | `status === "done"` |

Falls back to the positional rule when no `evidence` prop is passed.

## Schema change

`shotCount` was split, because fix #3 makes partial analysis possible for the
first time:

```
shotCount     = len(shots)      what scene detection found
shotsAnalyzed = shots_written   what has keyframes and can be compared
```

Detection and the empty-state branch read `shotsAnalyzed`. Both are attached to
`job_analysis_completed` with a `partially_analysed` boolean, so the divergence
is queryable rather than silent.

`shotsAnalyzed` is absent on jobs written before today — treat undefined as
equal to `shotCount`.

**Modal secret `posthog-api-key`** — holds `POSTHOG_API_KEY` and `POSTHOG_HOST`
(EU Cloud, `https://eu.i.posthog.com`). Created by the account owner, not by
tooling. No hardcoded fallback for either value; if the secret is incomplete

## Known gaps

- **Events not visually confirmed inside PostHog.** The `phc_` project key is
  write-only; querying the events API needs a personal API key. Evidence is the
  absence of `analytics: … capture failed` in Modal logs, which is weaker than
  seeing them land.
- **`outcome:"empty"` not observed.** After fix #1 it only fires on total
  keyframe failure across every shot — a genuinely rare path. Deliberately not
  forced with a contrived input.
- **`job_analysis_failed`** was triggered with an audio-only file rather than
  waiting for the intermittent keyframe crash.

## Explicitly out of scope (owner's call, untouched)

- The **5 credits vs "1 fix/month"** contradiction. `PLAN_LIMITS.free.creditsPerMonth
  = 5` means 5 *seconds* of Runway output, while `calcCreditsNeeded` charges the
  full target-shot duration per error — so one error on any shot longer than 5s
  exceeds a new user's entire monthly allowance. This is why every
  `fix_quota_exceeded` fires within 500ms of `fix_requested`. The UI does route
  to `/pricing` via a "See plans →" link; it is not a dead end.
- The `0.5` min free cap value.
- Detector thresholds and the `>=2` / `>=3` shot requirements.
- Stripe checkout. Note that `credits_checkout_started` fires only *after* a
  successful checkout response, so it cannot distinguish "nobody tried" from
  "checkout is broken".
- `MODAL_REPROCESS_URL` — missing from `.env.local`, read with a non-null
  assertion at `lib/modal.ts:32`. TODO added, not fixed.
