# Session 2026-08-25 — the fix pipeline could not complete, and had not since 30 July

Started as "free users keep hitting quota exceeded, should we raise the
quota?". The quota was real but it was the smallest of five independent
defects, three of which made a completed fix impossible for anyone at any
price.

---

## The reported problem

Free and paying users hitting `fix_quota_exceeded`, and a paying customer
charged $19 on 23 August who received nothing. A fix-pipeline brief on the
desktop laid out five suspected bugs and an execution order.

**The premise was half right.** The quota was genuinely unusable — 5 credits
could not cover a single ~10-second shot, so no free user could ever finish
one fix. But raising it would have changed nothing, because **no fix could
complete regardless of credits**.

---

## The five defects

### 1. `gen4_aleph` reached its sunset date on 2026-07-30

Every Runway submission had 400'd for 26 days:

> `gen4_aleph was deprecated and reached its sunset date on 2026-07-30; it no
> longer accepts new generations. Use "aleph2" for /v1/video_to_video.`

Found stored verbatim on error `HfTmvLns…` of the 12 August job.

**This was nearly missed.** An early check of the Runway API reported a valid
key and a healthy 236,172-credit balance, and the model appeared in
`/v1/organization`'s tier listing — so Runway was wrongly ruled out. That
endpoint lists rate limits per model, not whether a model still serves.

Migrated to `aleph2`. Not a drop-in; verified against the live OpenAPI spec
(`docs.dev.runwayml.com/openapi.json`) rather than assumed:

- `ratio` is deprecated on `aleph2` — no longer sent
- `references` **does not exist**; nearest equivalent is `keyframes`
  (`{uri, seconds}`, up to 5, `range` deliberately omitted since it
  *restricts* the edit window)
- `promptText` caps at 1000 chars
- `X-Runway-Version: 2024-11-06` unchanged

Each shape was probed against the live validator using a deliberately
unfetchable `videoUri`, so schema errors separated cleanly from asset errors.

### 2. Every fix was cancelled at ~300s by its own caller

The whole fix ran inline inside a Modal web endpoint:

```
Vercel route → after() → fetch(fix_phase) → Modal runs the fix inline
      Modal 303s past ~150s; Vercel kills after() at its 300s limit
      connection drops → Modal cancels the in-flight function
```

An `aleph2` generation takes minutes, so every fix was killed part-way —
**after Runway had already been charged** — leaving the job stuck in `fixing`
with no output and no error. Reproduced three times manually before the
pattern was recognised (840 credits of debugging).

Split into a detached `run_fix_phase` worker plus a thin webhook that
`spawn()`s it and returns immediately. Measured: 0.5s instead of a held
connection. Runway poll budget 12 → 20 min and worker timeout 1800 → 7200s,
both of which `gen4_aleph`'s speed had been hiding.

### 3. Server-side events were captured but never flushed

`capture()` queues; the HTTP POST was never awaited. On serverless the
instance freezes when the response returns, so the event was simply lost.

This is why fix requests looked "silent". Replaying the route's exact logic
against every silent job's real documents showed **all of them reached the
quota check and correctly returned 402** — the same branch that *did* emit for
the paying customer minutes earlier. Not a code path difference; event loss.
Corroborated by 38 job docs vs 35 `job_created` events in the window.

`captureServer()` captures and awaits the flush. All server captures now go
through it.

### 4. No Stripe webhook endpoint existed

The handler had been in the codebase all along. Stripe had three registered
endpoints — `ahumans.com`, `albusi.com`, `imgero.com` — and **none for
Scene Fixer**. Event `evt_1U8JU4…` fired at 13:11:50Z with correct metadata
(`plan: pro`, `uid: 2c2hc…`) and `pending_webhooks: 1`. It was never delivered
to us, so `plan` was never written, so `plan ?? "free"` gave her 5 credits two
minutes after paying.

The webhook and a manual admin route are the *only* writers of `plan` anywhere
in the codebase.

### 5. User documents were created without an entitlement shape

`/api/jobs/[id]/start` created `users/{uid}` with a merge of only
`{ scanDate, scansToday }`. **All 28 existing user documents were incomplete** —
not one had the full shape. `lib/entitlements.ts` is now the single source of
truth and repairs partial documents on read.

## Credit accounting

Two bugs that made a non-fix look like a success:

- **A fix that threw kept the user's credits** and the job still reported
  `done` with an output that was just the re-encoded original. The 12 August
  job is the exact shape: `fixStatus: failed`, Runway sunset error,
  `creditsDeducted: 2`, `autoRefunded: false`, job `status: done`.
- **`error.get("creditsDeducted", 5)`** — a missing value minted five credits
  out of a malformed document. Same bug found and fixed in the Next.js manual
  refund route (`?? 5`).

Now: a thrown fix refunds its own credits; a job where every fix threw is
written `error`, not `done`, and stitch is skipped entirely so no re-encode is
ever presented as a result.

**And a fix that runs but fails verification is not a success either.** Added
`verificationPassed`; the ambiguous `fixesSucceeded` was removed in favour of
`fixesVerified` / `fixesUnverified` / `fixesFailed`. `status` stays `done`
because a dozen call sites gate re-fix, reprocess, retry and download on it —
a new enum value would have broken all of them silently. UI shows "Result
available — not a fix", the final progress step does not tick, and the jobs
list reads "Not fixed".

## Entitlements

- Free grant **5 → 30** credits (two ~10s fixes). At 5, a single 10s shot cost
  11 and no free user could ever complete one fix.
- **Email verification is the wrong gate.** Google OAuth is the only signup
  path, so `emailVerified` is `true` for every account — including
  `thelilithshow@thelilithshow.com`, whose domain returns **ENOTFOUND on both
  MX and A**. Every transactional email to it had hard-bounced since signup.
  Deliverability (MX with A fallback, failing open on resolver errors) is the
  real gate. Across all 28 accounts it flags exactly one: the paying customer.
- Per-account `MONTHLY_SPEND_CEILING` (free 30 / starter 120 / pro 300 /
  studio 800) as a blast-radius cap on a prepaid pool.
- One concurrent fix per free account, with stale `fixing` jobs excluded.
- Self-serve cancellation via Stripe Billing Portal. `/legal/refunds` already
  told customers they could cancel from their account; they could not.

**Known inversion:** free (30) now exceeds starter (20). Deliberate — paid
grants are frozen until ~20 real fixes give a measured cost-per-fix. Marked in
`lib/types.ts`. Should not survive the reprice.

## Instrumentation

Every fix request now resolves to exactly one terminal event:
`fix_started` / `fix_quota_exceeded` / `fix_rejected` (with a distinct reason:
`unauthorized`, `job_not_found`, `not_fixable_state`, `no_unfixed_errors`,
`email_not_verified`, `email_undeliverable`, `concurrent_fix_limit`,
`monthly_ceiling_reached`) / `fix_failed`, preceded by a server-side
`fix_request_received`.

Also: `error_confirmed` moved server-side (proves the Firestore write, not the
click); `fix_completed` carries real Runway cost, shot duration and resulting
balance; the Stripe webhook emits `stripe_webhook_received` /
`stripe_webhook_rejected` and reads back the entitlement write, emitting
`entitlement_write_failed` if `plan` did not persist.

## Verification

**End-to-end on a fresh account against production:**
signup → ID token → `POST /api/jobs` → signed upload → `/start` → analysis →
`/confirm` → `/fix` → terminal `done`, `attempted=1 verified=1 failed=0`,
output file H.264 854×480 + AAC, 10.04s, 480p watermarked.

User document created on first request with the **complete** shape — the
defect from §5 confirmed fixed on the exact path that created all 28 broken
documents.

Credit accounting exact: 10.006s shot → 11 credits → deducted 11 → 19 of 30
remaining → verification failed → **11 refunded** (not the old hardcoded 5).

**Forced failure path** (confirmed error pointing at a missing shot, throws
before any Runway call): job `error` not `done`, no output URL, error marked
failed, `refundReason: fix_threw`, 5 refunded.

Test artifacts removed from production afterwards.

## Real unit economics — first measurement since launch

`aleph2` charged **280 credits for a 10.006s shot = 28.0 credits/sec =
$2.80 per 10-second fix**, exactly the documented rate.

Banked 236,172 credits ÷ 28 = **8,434 seconds** of output. At a 30-credit free
grant that is ~281 free-user-months. No cash cost, but finite.

Runway 236,172 → 234,772 this session (1,400 used; 840 of it cancelled
debugging runs).

## Free-user viability, checked against real data

17 real jobs with detected errors:

- **Cheapest single fix exceeds the 30-credit grant: 0 of 17.** Max is 24.
- Median single fix 11 credits → 2 fixes/month, matching the copy.
- **But 4 of 17 (24%) exceed 30 if the user confirms every detected error**,
  and the fix route is all-or-nothing — it fixes nothing and says "upgrade"
  when deselecting one error would have worked. No cost is shown anywhere
  before the click. *Not fixed; flagged.*

**Funnel: 62% of jobs never reach a fixable state.**

| Outcome | Count |
|---|---|
| Found errors (fixable) | 17 |
| Analysed clean | 10 |
| Zero shots | 9 |
| Stuck `uploading` | 6 |
| Errored / too long | 3 |

The **9 zero-shot jobs were all correctly rejected for exceeding the 30s free
cap** (30.79s–83.56s) — `decompose` set `status: error`, then `run_detect`
overwrote it back to `awaiting_confirmation`, stranding the reason in a field
nothing rendered. Already fixed 17 August; these are historical residue. No
format/codec/resolution pattern — duration was the only common factor.

The **6 stuck-uploading jobs are a live, unfixed leak**: no `inputVideoUrl`,
no object in the bucket — the browser PUT never completed and nothing marks
the job failed. Four are one user retrying within 75 seconds. *Diagnosed only.*

## Copy

Free tier stated in fixes, not credits: "2 free fixes per month, up to 10
seconds each". The old "5 credits / month (~1 fix)" was both wrong and asked
the reader to do arithmetic in an internal unit to find out.

Length-limit message stated both sides in the same unit. It read "supports up
to 0.5 min, but this video is 1.3 min" for a 30.79s clip — a contradiction on
the last screen before a purchase decision. Now "supports up to 30 seconds,
but this video is 31 seconds", forced to seconds on both sides whenever the
cap is under a minute.
